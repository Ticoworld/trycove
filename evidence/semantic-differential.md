# DripFund × Cellora: source and controlled-fixture investigation

On 2026-11-16, `scripts/semantic-run.sh` completed with **exit 0**. Raw stdout, stderr and SHA-256 hashes of both logs and the harness are in `semantic-execution.stdout`, `.stderr` and `.sha256`. Verify with `sha256sum -c evidence/semantic-execution.sha256`; run again with `scripts/semantic-run.sh` after installing project dependencies and ensuring the pinned Node image named in the script is available locally. Network is needed to fetch the two pinned Git revisions and one npm tarball; it is unavailable inside the execution container.

The script verifies SHA-256 of the exact Cellora API route, database query and FSL-1.1-ALv2 license; verifies DripFund's exact indexer and lockfile; checks the npm `@ckb-ccc/core` 1.12.2 artifact against DripFund's lockfile SHA-512 integrity before reading its source. DripFund `package.json` declares `@ckb-ccc/shell` as `*`; the checked-in lock resolves shell 1.1.22 and core 1.12.2, which does not prove the deployed application's dependency versions.

Actual DripFund `fetchRecentDonations` code ran against a synthetic CCC stub and deliberately modeled Cellora-style rows: explicit live/data returned Alice; a modeled unfiltered response returned Alice and Bob; omitted data returned zero. When the stub changed the ordering of two equal-block fixtures, DripFund's block-number sort preserved the different input order. These are counterexamples showing sensitivity to input conditions, **not execution of the Cellora service**, not proof that CCC supplied these orders, and not proof of historical-accounting correctness. Transaction hashes and identities in the fixture are synthetic labels.

The checked Cellora source separately establishes `include_data` opt-in, unspecified liveness mapped to any, a 32-byte lock/type hash filter, and descending block/transaction/output cursor order. The locked CCC artifact shows exact script search and cache-first iteration, with the order argument documented as applying only to RPC results. DripFund additionally asks CCC for transaction headers and uses the returned timestamp; the Cellora cell response does not itself supply that timestamp. A real adapter must verify CKB script serialization and hashing, pagination and state semantics, reorg handling, auth, a source of header timestamps, and the intended treatment of consumed donations. No actual chain, testnet deployment, signing, real wallet, or network transaction was exercised.

Only the hash-checked DripFund source is transpiled and executed, inside a Docker container with `--network none`, read-only filesystem and input mount, no capabilities, `no-new-privileges`, non-root uid, bounded CPU/memory/PIDs, and a 30-second timeout with cleanup. The CCC and Cellora behavior are stubbed/modeled; the reviewed Cellora code is only read and is not copied into Trycove or executed. Docker isolation depends on the host daemon's normal security guarantees and is not a proof of a hardened multi-tenant sandbox. Node v24.22.3 ran in pinned image `node@sha256:116b800c3754b440ee0aa3ed2f20f5bf3d99a554bfd9adeea09ea8017f6e85f5`; host TypeScript was 5.9.3.

Cellora's license permits listed non-commercial research but restricts competing commercial use and places terms on redistribution and derivatives. A commercial integration must assess that license in its actual context. No license file was found at the inspected DripFund repository root; this experiment retains neither its source nor its compiled output, which are fetched into a temporary directory and deleted on exit.
